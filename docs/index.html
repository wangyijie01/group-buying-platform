02 / Business journey

正向交易与逆向补偿，
都能讲清楚。

每一步都有明确的状态归属、事务边界和失败出口，适合用于复盘高并发库存、幂等消费与最终一致性问题。

运营配置

活动、折扣、渠道商品和人群标签建立关联。

首页试算

规则树并行加载数据，计算优惠并判断资格。

下单锁单

商城建单，拼团责任链预占队伍名额。

支付回调

渠道确认付款，商城落库后发起营销结算。

拼团结算

更新完成人数，达到目标后推进整团完成。

成团履约

HTTP / MQ 通知商城，将订单推进到履约阶段。

定时补偿

主动查单、超时关单、通知重试和名额释放。

退款逆向

按支付与成团状态选择策略并异步追平。

03 / Engineering decisions

设计模式不是装饰，
每个都解决具体复杂度。

从试算编排到库存预占，再到跨服务补偿，技术选择直接对应业务变化频率与失败概率。

RULE TREE

规则树拆解营销试算

Switch、Market、Tag、End 等节点隔离系统控制、数据加载、优惠计算和标签过滤；活动与 SKU 通过线程池并行加载。

CHAIN

责任链守住交易入口

锁单、结算和退款分别维护独立校验链；新增规则只扩展过滤器，不让核心服务退化为大型 if-else。

ATOMIC + CAS

缓存拦截，数据库兜底

Redis 原子计数承担热点预占，分段幂等键处理重复序号，MySQL 条件更新提供最终人数约束。

BITMAP

标签在线判断 O(1)

离线任务产出用户标签，结果落明细表并同步 Bitmap；活动级标签控制资格，折扣级标签控制差异化优惠。

OUTBOX-LIKE

本地任务表保存失败现场

业务状态与通知任务在本地事务中一起落库；下游不可用时保留重试证据，不依赖一次 HTTP 或 MQ 必须成功。

DCC

配置变更无需重新发版

注解标记业务字段，Redis 发布订阅广播变更，反射更新降级、灰度和黑名单参数。

04 / Reliability loop

不追求“一次成功”，
追求“最终可收口”。

幂等、落库、异步与补偿各自解决不同失效点；组合起来，才能让支付与拼团两个领域的状态最终一致。

1本地事务更新队伍 / 订单状态，同时写入通知任务。
2HTTP 或 RabbitMQ 推动下游处理，消费者按业务键幂等。
3失败任务进入重试态，由定时作业再次投递。
4Redisson 锁避免集群重复扫描，最终失败保留审计状态。
